# Архитектура: как ученику перестать зависеть от автора

Коротко: подход не тупик (89 % с 20 рассказов против 45–54 % у трансформера), тупик — цикл «слепой набор → 3–5 рукописных частей». Причина видна в коде и в числах: составная часть грунта переносится на новых авторов, списочная — нет.

## Что я измерил

95 слепых задач A–H (H без шестой), по `results/rows/bridge_*.txt` и `final9/H_*.txt`. Скрипты: `scratch/brainstorm/` (`tab.py`, `lex.py`, `count.py`, `dsl_count.py`). Ученика я не запускал; отнесение провалов к причинам — моя разметка по README и выводам прогонов, задним числом.

- **Провал виден самому ученику.** Ниже 95 % — 43 задачи; в 42 из них он не объяснил и свои обучающие рассказы (среди 52 выученных таких 13). Где объяснено ≥ 98 % своих вопросов (50 задач), тест в среднем 98,9 %; в остальных 45 — 77,9 %. В этих 43 задачах 1005 из 1051 потерянного пункта.
- **Потери — в темах про порядок и числа.** «Сравнение по шкале» 73,1 % (ниже 95 % в 7 наборах из 8), «порядок во времени» 74,9 % (7 из 7), «количества» 77,9 %: вместе 54 % всех потерь. Темы, где ответ — обход по F и E (вместилища, обмен, роды, цепочки, группы, правила), дают 94–99,6 %.
- Шаги обхода составные (`F_STEPS`, `E_STEPS`, `walks()`), и новые авторы их почти не ломают. Порядок, количества, связи с направлением и время сделаны списком концовок, и их ломает каждый автор. Оговорка: эти темы могут быть и просто разнообразнее.

## 1. Почему каждому повороту нужен свой код

1. **Концовка — тупик, а не шаг.** `answer()` (records.py:576–815) — цепочка из 55–60 имён; концовка отдаёт готовую строку, дальше её не передать. Составляются только шаги по F и E, не длиннее двух. Пример, H3: «how many people are taller than X» = «сосчитать» ∘ «все, кто лежит в эту сторону». Обе половины есть (`count`, `lover`), но `lover` — концовка. При верном прочтении предложения `queries()` даёт этому вопросу **0 кандидатов** (проверил); ученик портит прочтение (link + tie2 + set), чтобы подошёл `count [>F0 >>E0]`. В H7 то же: «how many coins are there in all» — 0 кандидатов.
2. **Одно и то же написано много раз.** «Крайний из множества по ключу» — это most, least, over, under, utmost, utmostof, top, edge, pedge, eldest, newest, rank, first, last: 14 имён. Различия — откуда множество (все, названные, пары с вещью) и откуда порядок (E, L, Q, время, когда названа). Автор берёт клетку «источник × кого × что спросить × вид ответа»; закодировано 55 клеток из нескольких сотен. Этап 20 раскладывал руками: `at` — единственный настоящий комбинатор, и тот по списку `AT`.
3. **Предложение — только действие**, исполняемое в момент чтения. «The dinner is on the day after the picnic», сказанное раньше дня пикника (H12, 51,9 %), и события, заданные то часами, то «до/после» (E6, G6, H6), — условия, которые решаются к вопросу.
4. **Слово как параметр есть в четырёх концовках** (`TABLED`). «Loses» против «gets» (H7: читалка слила их в один `qadd`), «closes» → «closed» (A5, G5), пары противоположностей (в H3 три вида вопросов выбрали три разных набора пар) — то же самое, и каждый раз отдельная заплата.
5. **Оценка не в тех единицах.** Часть стоит `PRICE` = 0,25 вопроса, а выбирается одно из 35–461 прочтений предложения (замер; до 8,9 бита); вопрос «да/нет» несёт не больше бита. Прочтение принимается при свидетельстве на порядок слабее своей длины, поэтому «богаче грунт — больше ложных прочтений» — следствие устройства. G3: 13 видов вопроса по ~10 штук, каждому подобрана своя случайная программа.

## 2. Что строить

### A. Алгебра запросов вместо списка концовок

Каждое хранилище отдаётся как отношение, и к любому применимы одни операторы.

| тип | примитивы |
| --- | --- |
| отношение | `F_k`, `was_k`, `E_k`, `L_k[d]`, `pair` (вещь → пары с ней), `part`, `ord(ключ)`; `inv`, `R;R'`, `R+`, `R*`, `end`, `∪` |
| множество | `x.R`, `named(род)`, `all(род)`, `∩`, `−`, `{y∈S : число ⋚ число}` |
| число | `count(S)`, `Q_k(x)`, `ΣQ_k(S)`, `times_k(x)`, `#i`, `±` |
| вещь | `argmax/argmin(S, ключ или порядок)`, `nth` |
| да/нет | `x∈S`, `S≠∅`, `⋚`, `S=S'` |
| взгляд и выход | `at(#i)[…]`; назвать, по порядку, число, да/нет; `table[слово]` для любого параметра |

Около 30 операторов: реляционная алгебра с замыканием и агрегатами.

Нынешние концовки в нём: list = `x.R`; has = `y∈x.R`; some; count = `count(x.R)`; sum = `ΣQ(x.R)`; cmp, diff, cmpn; most/least = `argmax(named, Q)`; over/under = `argmax(named, E+)`; utmost = `argmax(all, O)`; utmostof = `argmax(named, O)`; top = `part(argmax(x.pair, Q))`; eldest/newest = `argmin(x.R, born)`; lover = `x.L[d]+`; lis; lhead/ltail; which = `{y∈all : Q(y)⋚#i}`; rank = `nth`; asof/wasat = `at(#i)[x.F]`; both = `x.R∩y.R'`; first/last = `argmin(named, time)`.

Слепые провалы: H3 = `count(x.L[d]+)`; H7 = `ΣQ(x.pair)` и `part({p∈x.pair : Q(p)>0})`; G3 = `argmax(named, L[table[w]]+)`; F8 = `{d : x∈y.L[d]+}`; F6 = `at(#i)[times(x)]`; E3, F3, F12 = `argmax(all, O)`. Это 46 % потерь наборов E–H: потолок +5 пунктов среднего. Не выражаются: E12 (счёт по кругу), H12, E6, G6 (условия), A5/G5/H5 (слово ↔ значение), F1/F2/G1/G2 (поиск и читалка).

Сколько кандидатов. Сейчас (замер на H): 0–90 на вид вопроса, 35–461 на предложение, все предложения задачи вместе — от 10^2,5 до 10^29 сочетаний. В алгебре на глубине до трёх (счёт по родам вещей H3, H7, G3; оценка, не настоящий перечислитель): от сотни до двух тысяч на вопрос с одной-двумя вещами, ~13 000 на вопрос с четырьмя, до 10^4 на «да/нет». В 30–100 раз больше нынешнего; без B и C это только добавит ложных прочтений.

### B. Одна оценка в битах

Длина = Σ log2(число альтернатив в точке выбора) + Σ по необъяснённым вопросам log2(число возможных ответов). Часть остаётся, если укорачивает сумму. Это заменяет `PRICE`, `EASE`, «вопрос на два новых вида», пороги 9/10 и 19/20, правило умолчаний — около десяти подобранных чисел. Параметры мира (пары противоположностей, знак количеств) платятся раз на задачу. G3 показывает, зачем общие формы: на один вид 10–16 бит данных против 13,7 бита выбора программы; на 13 видов вместе — 135 вопросов.

### C. Углубление по остатку

Для вида вопроса, объяснённого хуже 95 %, прочтение предложений замораживается, состояния в точках вопросов считаются один раз, и алгебра перебирается глубже только для него: 10^4–10^5 программ на 10–30 вопросах — секунды или минуты, без переигрывания рассказов. Не нашлось — ученик говорит «этот вид вопросов не понимаю» и не подгоняет. Это и есть сборка недостающей части без автора.

### D. Слоты вместо догадок читалки

Каждое чередующееся слово — слот; его роль решает тот же поиск той же оценкой: аргумент, ключ таблицы (выбирает ход, направление, знак) или лишнее. Три догадки `rows.py`, `aliases()` и `TABLED` становятся одним механизмом. G3: 2 вида вопросов вместо 13; G5: 4 вида предложений вместо 19; H7: `gets`/`loses` с выученным знаком. Прочтение с 82 (C7), 48 (B11), 41 (D9) видами предложений при брифе «1–3 шаблона на факт» свою цену не окупит.

### E. Память между задачами

Каждая задача учится с нуля. Замер: из 44 видов предложений набора H 24 дословно встречались в A–G; из 14 таких в выученных задачах H 13 получили уже встречавшееся прочтение; 50 из 59 слов шаблонов не новые. Таблица «слова шаблона → прочтение» даёт начальное прочтение всех предложений сразу и приор для B. Это лекарство от ложного первого шага: сейчас предложение оценивается только через вопросы, пока остальные не прочитаны. Позже — библиотека частых поддеревьев алгебры (без A сжимать нечего: концовки — атомы).

### F. Числа и времена как неизвестные

Хранилище условий «x = n», «x = y + n», «x < y» с распространением; `Q(x)` и время события читаются из решения. Заменяет `setat/setnext/setprev`, pis/pedge и «штампы» в `over()`; закрывает H12, E6, G6 (24 % потерь E–H). Это рукописная часть, говорю прямо.

Модель генератора автора не предлагаю: без языковой модели это список схем этапов 4–6 (71 % вслепую). Языковая модель, дописывающая часть по остатку под проверкой грунта, убрала бы автора буквально, но это чужой перебор; годится только как потолок для C.

## 3. Поиск и читалка: что меняется по существу

- Ложные прочтения: оценка в битах (B); крупные шаги (слот, второй ход, `together`, `aspects`) принимаются по отложенной пятой части своих рассказов, а не по порогу.

**Решающий опыт (день кода, минуты счёта, без поиска по предложениям).** Отдельный файл: вычислитель алгебры над `State`, строк 250. Список примитивов — тот, что выше, заморожен. Восемь видов вопросов: E3, F3, F6, F8, F12, G3, H3, H7. Прочтения предложений задаются руками (те, что ученик находит сам). Перечислить все программы до глубины 4, оценить на 20+20 обучающих рассказах, проверить на тесте. Смотреть: есть ли программа с ≥ 99 % на тесте; сколько кандидатов до неё по размеру; сколько разных по поведению программ объясняют обучающие рассказы так же. Проходит: 6 из 8 без нового примитива, до 10^4 кандидатов, не больше трёх соперников (их разводит спрашивание). Опровергает: 3 из 8 и меньше, либо по примитиву на вид, либо десятки неразличимых соперников.

**Риск «тот же список в другой записи»** настоящий. Хранилища и смыслы (счёт по кругу, геометрия `where()`, условия) останутся за автором, а часть хвоста — знание слов (дни идут по кругу, closes → closed), которого поиск по 20 рассказам не даст; оно приходит только из памяти E. Прогноз: не 3–5 рукописных частей на набор, а около одной, и остаток ученик называет сам, а не отвечает на 50 %. Мерить надо не среднее, а число рукописных частей на набор, и два слепых набора подряд без правок между ними (обновляется только память E). Если второй не ниже первого и оба ≥ 93–94 % — круг разорван. Это и нести в Colab вместе с сетью-подсказчиком, обученной на рассказах, сгенерированных из самой алгебры (этап 14 для языка): видеокарта нужна там.
